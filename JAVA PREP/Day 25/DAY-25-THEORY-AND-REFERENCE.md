## Subtopics

### Relational model, DDL, and constraints

#### What it is

A relational database stores facts in **tables** (relations) made of typed columns and rows. **DDL** (`CREATE`, `ALTER`, `DROP`) defines the shape; **constraints** (`PRIMARY KEY`, `FOREIGN KEY`, `UNIQUE`, `NOT NULL`, `CHECK`, `DEFAULT`) let the database itself reject impossible data. Think of constraints as *executable business rules that no application bug can bypass*.

#### Why it exists / why it matters

Application code has bugs, multiple services write to the same database, and people run ad-hoc scripts. Only the database sees every write, so integrity rules belong there. PostgreSQL also gives rich types (`BIGINT`, `NUMERIC`, `TIMESTAMPTZ`, `UUID`, `JSONB`) so values are validated at the storage layer.

#### Pros and cons

**Pros**

- Integrity is enforced for every writer, not just your service
- Constraints document the model and help the query planner
- Fail-fast: a bad insert fails immediately instead of corrupting reports months later
- Identity/serial columns give stable surrogate keys

**Cons / trade-offs**

- DDL changes are heavy in production (locks, rewrites) and need migrations (Flyway/Liquibase)
- Over-constraining early can slow prototyping
- Cross-row rules (e.g. 'max 3 active orders') need triggers or application logic

#### What happens without it / when misused

Without NOT NULL/UNIQUE/FK, you get orphan rows (`orders` with no customer), duplicate emails, negative prices and `NullPointerException`s far from the cause. Typical symptom in Java: a `SQLIntegrityConstraintViolationException` at runtime — or worse, no exception and silently inconsistent data.

#### Syntax and rules

```sql
CREATE TABLE t (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  email VARCHAR(120) NOT NULL UNIQUE,
  qty INT NOT NULL CHECK (qty > 0),
  parent_id BIGINT REFERENCES parent(id)
);
```
Gotchas: `NULL` is not equal to anything, so `UNIQUE` allows many NULLs; `CHECK` passes when the expression is NULL (unknown); PostgreSQL folds unquoted identifiers to lower case (hence `DATABASE_TO_LOWER=TRUE` in H2).

#### Examples

**Example 1 — Table with CHECK and DEFAULT**

```sql
CREATE TABLE products (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  sku VARCHAR(30) NOT NULL UNIQUE,
  price_cents INT NOT NULL CHECK (price_cents >= 0),
  active BOOLEAN NOT NULL DEFAULT TRUE
);
```

**Example 2 — Foreign key with ON DELETE**

```sql
CREATE TABLE orders (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  customer_id BIGINT NOT NULL REFERENCES customers(id) ON DELETE RESTRICT
);
-- DELETE FROM customers WHERE id = 1  => error while orders reference it
```

**Example 3 — Proving a constraint from JDBC**

```java
try (Statement st = c.createStatement()) {
    st.execute("insert into customers(email, full_name) values ('a@x.io','A')");
    st.execute("insert into customers(email, full_name) values ('a@x.io','B')"); // throws SQLException (unique)
}
```

#### Quick checks

1. Why does `UNIQUE(email)` still allow two rows with NULL email?
2. Which constraint stops an order pointing at a missing customer?
3. Why put a CHECK on `price_cents` if the service validates it already?

### DML: INSERT, UPDATE, DELETE and RETURNING

#### What it is

**DML** changes data. `INSERT` adds rows, `UPDATE ... SET ... WHERE` changes matching rows, `DELETE ... WHERE` removes them. PostgreSQL adds `RETURNING` to get generated values back in the same statement; JDBC reports affected rows via `executeUpdate`.

#### Why it exists / why it matters

Every write path of a backend ends in one of these statements. Knowing exactly how many rows each touches (and that the WHERE decides) prevents the classic 'updated the whole table' incident.

#### Pros and cons

**Pros**

- Set-based: one statement changes thousands of rows atomically
- Affected-row counts give cheap optimistic checks
- `RETURNING` avoids a second round trip for generated ids
- DEFAULT values keep inserts short and consistent

**Cons / trade-offs**

- A missing WHERE is silent and catastrophic
- Large updates hold locks and bloat tables (MVCC dead tuples in PostgreSQL)
- `DELETE` is not recoverable without a backup or a soft-delete column

#### What happens without it / when misused

Forgetting WHERE changes every row; updating by a non-unique column changes more rows than intended; relying on column order in `INSERT INTO t VALUES (...)` breaks when a column is added. Symptom: `executeUpdate` returns a number you did not expect.

#### Syntax and rules

```sql
INSERT INTO t (a, b) VALUES (1, 'x');            -- always list columns
UPDATE t SET b = 'y' WHERE a = 1;
DELETE FROM t WHERE a = 1;
INSERT INTO t (b) VALUES ('z') RETURNING id;      -- PostgreSQL
```
Run risky statements first as `SELECT` with the same WHERE; in psql wrap them in `BEGIN; ... ROLLBACK;` while rehearsing.

#### Examples

**Example 1 — Targeted update**

```sql
UPDATE accounts SET balance_cents = balance_cents + 500 WHERE status = 'ACTIVE';
```

**Example 2 — Insert relying on defaults**

```sql
INSERT INTO accounts (id, owner, balance_cents) VALUES (5, 'eve', 100);
-- status becomes 'ACTIVE' from the column DEFAULT
```

**Example 3 — Affected rows in JDBC**

```java
int n = st.executeUpdate("delete from accounts where status = 'CLOSED'");
System.out.println(n + " row(s) deleted");
```

#### Quick checks

1. How do you preview what an UPDATE will touch?
2. Why list the columns in INSERT?
3. What does `executeUpdate` return for `DELETE`?

### Keys and normalization (1NF–3NF)

#### What it is

A **primary key** uniquely identifies a row; a **foreign key** references another table's key; a **composite key** uses several columns. **Normalization** removes redundancy: **1NF** atomic values and no repeating groups, **2NF** every non-key column depends on the whole key, **3NF** no non-key column depends on another non-key column.

#### Why it exists / why it matters

Redundant data must be updated in many places and drifts out of sync (update anomalies). Normalized schemas store each fact once, which keeps writes cheap and correct; reads then join tables.

#### Pros and cons

**Pros**

- Each fact stored once => no update/insert/delete anomalies
- Smaller rows, better cache usage
- Constraints become simple and exact
- Easier schema evolution

**Cons / trade-offs**

- More joins on reads (mitigated by indexes and views)
- Over-normalization hurts readability and performance for reporting
- Surrogate keys hide natural uniqueness unless you add UNIQUE on the natural key

#### What happens without it / when misused

A flat table `orders(customer_name, customer_email, product_name, ...)` renames a customer in 1,000 rows; one is missed and reports show two spellings. Other symptom: `UPDATE` anomalies, orphaned detail rows, impossible-to-delete data.

#### Syntax and rules

Rules of thumb: choose a stable surrogate PK (`BIGINT` identity or `UUID`), add UNIQUE on natural keys (email, sku), model many-to-many with a join table whose PK is the pair, keep money in integer cents or `NUMERIC`.
```text
flat(order_id, cust_email, cust_name, sku, prod_name, qty, price)
 -> customers(id, email, name)
 -> products(id, sku, name, unit_price)
 -> orders(id, customer_id)
 -> order_lines(order_id, product_id, qty)   PK(order_id, product_id)
```

#### Examples

**Example 1 — Detect a 2NF violation**

```text
order_lines(order_id, product_id, qty, product_name)
product_name depends only on product_id (part of the key) -> move it to products
```

**Example 2 — Migrating data with INSERT ... SELECT**

```sql
INSERT INTO customers (email, name)
SELECT DISTINCT customer_email, customer_name FROM raw_orders;
```

**Example 3 — Join table**

```sql
CREATE TABLE student_course (
  student_id BIGINT REFERENCES student(id),
  course_id  BIGINT REFERENCES course(id),
  PRIMARY KEY (student_id, course_id)
);
```

#### Quick checks

1. What problem does 3NF remove?
2. Why does a many-to-many relation need a third table?
3. When is denormalization acceptable?

### ACID transactions

#### What it is

A **transaction** groups statements into one logical unit. **A**tomicity: all or nothing. **C**onsistency: constraints hold before and after. **I**solation: concurrent transactions do not see each other's half-done work (to a configurable degree). **D**urability: once committed, data survives crashes (write-ahead log).

#### Why it exists / why it matters

Money transfers, order placement and inventory updates need several statements to succeed together. Without transactions a crash between debit and credit destroys money.

#### Pros and cons

**Pros**

- Correctness under failure (atomicity + durability)
- Concurrency without corrupting data (isolation)
- Simple mental model: `BEGIN` ... `COMMIT`/`ROLLBACK`
- PostgreSQL MVCC lets readers not block writers

**Cons / trade-offs**

- Longer transactions hold locks/snapshots and hurt throughput
- Higher isolation levels cost performance and can abort with serialization failures
- Distributed transactions across services are hard (later: sagas/outbox)

#### What happens without it / when misused

Autocommit on + two UPDATEs: the first commits alone; an exception before the second leaves money debited but not credited. Isolation issues: dirty read (uncommitted data), non-repeatable read, phantom read, lost update.

#### Syntax and rules

```sql
BEGIN;
UPDATE accounts SET balance_cents = balance_cents - 3000 WHERE owner = 'ana';
UPDATE accounts SET balance_cents = balance_cents + 3000 WHERE owner = 'bob';
COMMIT;   -- or ROLLBACK;
```
JDBC: `c.setAutoCommit(false)` ... `c.commit()` / `c.rollback()`. Isolation (SQL standard): READ_COMMITTED stops dirty reads, REPEATABLE_READ also non-repeatable reads, SERIALIZABLE also phantoms. PostgreSQL default is READ COMMITTED.

#### Examples

**Example 1 — Atomic transfer**

```sql
BEGIN;
UPDATE accounts SET balance_cents = balance_cents - 3000 WHERE owner = 'ana';
UPDATE accounts SET balance_cents = balance_cents + 3000 WHERE owner = 'bob';
COMMIT;
```

**Example 2 — Constraint-driven rollback**

```java
c.setAutoCommit(false);
try {
    st.executeUpdate("update accounts set balance_cents = balance_cents - 999999 where owner = 'ana'"); // CHECK fails
} catch (SQLException e) {
    c.rollback();
}
```

**Example 3 — Isolation anomaly table**

```text
dirty read           -> prevented by READ COMMITTED
non-repeatable read  -> prevented by REPEATABLE READ
phantom read         -> prevented by SERIALIZABLE (standard)
```

#### Quick checks

1. Which ACID property does the write-ahead log mainly provide?
2. What happens to partial work on ROLLBACK?
3. Which anomaly does READ COMMITTED still allow?

## Interview corner

**Q1. Difference between PRIMARY KEY and UNIQUE?**

Both enforce uniqueness; a table has one primary key (implies NOT NULL) but can have many UNIQUE constraints.

**Q2. What is a foreign key and what does ON DELETE CASCADE do?**

A FK references a parent key; CASCADE deletes dependent rows automatically when the parent is deleted (use deliberately).

**Q3. Explain 1NF, 2NF, 3NF briefly.**

1NF atomic columns; 2NF no partial dependency on part of a composite key; 3NF no transitive dependency between non-key columns.

**Q4. What does ACID stand for and which is hardest in distributed systems?**

Atomicity, Consistency, Isolation, Durability; atomicity/isolation across services is hardest (sagas, outbox).

**Q5. Why store money as integer cents or NUMERIC, not DOUBLE?**

Binary floating point cannot represent decimal fractions exactly; rounding errors accumulate.

## Common mistakes & debugging

- Forgetting that H2 `MODE=PostgreSQL` is only an approximation — verify final scripts in real PostgreSQL 17.
- Splitting scripts on `;` while a string contains a semicolon (`SqlLab` is intentionally simple).
- Using autocommit for multi-statement business operations.
- Running `UPDATE`/`DELETE` without WHERE; always preview with SELECT.

## Answers

### Relational model, DDL, and constraints

1. In SQL NULL means unknown, and NULL = NULL is not true, so no two NULLs are considered duplicates.
2. A FOREIGN KEY (`REFERENCES customers(id)`).
3. Other writers and future bugs bypass the service; the database is the last line of defence.

### DML: INSERT, UPDATE, DELETE and RETURNING

1. Run `SELECT * FROM t WHERE <same predicate>` first (or `BEGIN` ... `ROLLBACK`).
2. The statement keeps working when columns are added or reordered and is self-documenting.
3. The number of rows deleted.

### Keys and normalization (1NF–3NF)

1. Transitive dependencies: non-key columns that depend on other non-key columns, causing redundancy.
2. A single column cannot hold multiple foreign keys atomically (1NF); the join table stores one row per pair.
3. For measured read-performance needs (reporting, caches), accepting duplicated data and the responsibility to keep it in sync.

### ACID transactions

1. Durability (and it enables atomic rollback/recovery).
2. It is discarded; the database returns to the state at BEGIN.
3. Non-repeatable reads and phantoms.
